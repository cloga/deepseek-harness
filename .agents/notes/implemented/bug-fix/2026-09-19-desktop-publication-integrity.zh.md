# Agent Note: 在公开发布前验证 Desktop 发行完整性

Status: implemented

[English](2026-09-19-desktop-publication-integrity.md) | 中文

## 问题

分支 Desktop 工作流在一个 PowerShell 步骤中调用多个原生 `gh` 命令，却没有逐条检查退出状态。因此，草稿创建或附件上传失败后，仍可能继续执行公开发布命令。源码、标签和远端附件检查只发生在公开之后，而且仅检查返回的附件可能漏掉缺失文件。不可变发行版无法在这些检查失败后修补。

## 决策

[受检查的发布器](../../../../apps/desktop/scripts/publish-fork-release.mjs) 使用 Node 内置模块和明确的 GitHub API 结果，替代未逐条检查的原生命令序列。发布任务检出精确的构建源码，并在调用发布器前验证下载产物集合的摘要。该任务无需额外安装依赖包。

只有明确分类的 HTTP 404 才能证明对象不存在。发布器验证已审阅的清单输入，拒绝已有发行版或标签，创建指向已审阅提交的新轻量标签，并创建属于本次操作的草稿。公开前必须核对草稿身份、源码、标签，以及完整附件集合的名称、数量、大小和摘要；公开后再次验证不可变结果。凭据仅发送到 GitHub API 和明确的上传端点，不跟随重定向。

任何失败或结果不确定的操作都会停止后续步骤。不自动重试写入、不移动标签、不编辑既有草稿，也不自动执行清理写入。中断后保留的标签或草稿需要明确核对，不能因此获得发布其他写入者附件的权限。

## 考虑过的替代方案

**只在原生命令失败时停止。** 这可以堵住一处错误传递缺口，但源码和缺失附件检查仍然发生在不可逆的公开发布之后。

**发布后再修补。** 不可变附件和标签刻意禁止这种恢复方式。验证应当发生在公开前；公开后的验证是额外检查，而不是首次检查。

## 后果

离线负向测试覆盖传输和 API 错误、归属冲突、源码或标签不匹配、不完整附件集合及发布失败。工作流测试要求在产物集合校验后运行精确源码中的发布器。这些防护不改变 Desktop 运行时行为、Core 或依赖版本、安装器交互，以及安装前必须另行征得用户同意的要求。
