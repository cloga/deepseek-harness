# Agent Note: 替换 Desktop profile 前保护用户插件清单

Status: implemented

[English](2026-09-19-desktop-user-inventory-guards.md) | 中文

## Problem

运行时状态文件缺失，不代表 Desktop profile 是首次创建。在 staging 之前重新初始化 manifest（元数据清单），会移除插件声明，即使后续健康检查失败也无法撤销。Release plan 健康不能证明已禁用或计划外的用户插件仍在；optional 同名替换也可能在获取失败时丢弃原有手动安装。

来源 receipt、来源 lock、依赖 specifier 与产物文件可能互相矛盾。仅凭 ownership 标签不能授权替换这些声明。恢复控件也能销毁 profile 内容，因此点击重置操作本身不构成知情确认。

## Decision

Profile 初始化在任何写入前拒绝已有包、运行时或保留的 Desktop 组合元数据。规范路径的 `lstat` 检查遵循实际文件系统的大小写语义，也能识别失效链接。无关文件不阻止真正的新 profile 初始化。孤立的用户元数据及矛盾的依赖、来源声明需要人工检查，而不是隐式重建。

每次事务在 prune 或包操作前捕获用户依赖 specifier、启用标记、receipt 身份与 owner、来源 lock 和已验证的产物摘要。保护范围包括已禁用插件与合法无 receipt 的 registry 包。只有 receipt、产物引用与声明一致且没有冲突 source lock 时，release ownership 才能把声明排除在用户清单之外。检查发生在 staged 准备及健康检查后、替换前仍活动的 profile 上，以及最终 Host 激活后、提交前。失败沿既有回滚路径处理。

显式安装和更新只能改变获取过程确定的目标包名；私有获取结果携带该名称，不改变公开 receipt 结果。目标在健康检查前准备好的身份和存在性被固定，目标名称例外不意味着允许丢掉该包。删除要求目标声明消失，不要求其损坏的产物字节可用。Toggle 只改变指定启用标记，disable-all 只改变启用标记。

Release plan 不得自动接管冲突的手动安装。只有已启用、user-owned 且验证来源与计划完全相同的包才能自动重建。不同的来源、版本、commit、产物、安装类型或用户禁用状态需要显式用户操作。Optional 重建失败且会移除受保护包时，整次事务失败。

普通启动 IPC 和不依赖 preload 的应急重置入口都必须取得原生破坏性操作确认，默认选择取消，然后才停止 Host 或修改 profile 文件。取消会恢复恢复操作控件；退出应用或关闭所属窗口会使迟到的确认失效。在持有锁并停止 Host 后，重置会先验证配置和产物的私有副本，再执行首次破坏性写入。生成的 node_modules 不复制；配置链接会拒绝重置。复制失败会尝试重启原 Host，最终就绪或失败则写入独立的不可变结果。

本决策部分取代[归属决策](2026-09-17-desktop-plugin-retention-and-lockfiles.zh.md)和[验证事务决策](../architecture/2026-09-15-desktop-verified-release-plugin-transactions.zh.md)中的 desired 同名优先级及 optional 失败排除规则。其来源验证、归属迁移、锁文件规范化与常规激活回滚仍然适用。公开 IPC、插件 receipt、来源和 Session schema 保持不变；私有激活 journal 版本 2 增加恢复证据。

## Recovery evidence

版本 2 的 journal 将操作及获取确定的目标名称，绑定到前后清单指纹，内容包括已验证声明、归属、来源 lock、引用产物字节、运行时状态、lockfile 和 workspace 元数据。生成的 node_modules 和 Host 文档不参与。恢复在任何重命名或清理前检查全部残存 profile 候选。旧 journal 没有历史指纹：关键元数据不完整或手动清单不同，会保留候选供检查。活动元数据缺失且存在孤立 rollback 不属于首次安装；健康活动 profile 不会仅因无关的孤立 staging 而被阻止。

Journal 写入使用独占随机临时文件、完整写入、同步和原子替换，不使用可预测且会截断已有文件的临时路径。保留的审计记录在 journal 清理后仍然存在，仅包含操作类型、目标包、事务 id、清单 hash/名称和结果。私有审计限制保留组数，也计入部分写入，从不序列化来源 URL、原始错误、配置或提示词。变更前发布审计失败会拒绝操作；写入 committed journal 后失败则保留它及 rollback 以进行验证恢复，不把提交重新标成失败。

重置副本位于活动 profile 之外，最后发布验证 receipt，并保留失败结果和部分证据。它们不是自动恢复指令，且可能包含私有配置。这些机制同步文件数据，但不承诺断电后的文件系统目录持久性。

## Alternatives considered

**把运行时状态缺失当作首次安装。** 这会在回滚副本存在之前覆盖活动声明，之后发生失败也无法撤销该写入。

**只保护启用或带 receipt 的包。** 已禁用插件仍属于已安装清单，registry 包合法地没有 receipt，来源快照则使用独立 lock 存储。

**豁免所有 desired 或显式点名的包。** 出现在计划中不代表获得替换手动来源的授权。即使用户明确要求安装，该包也必须在健康及激活回调后保留准备好的身份。

**从损坏元数据推断用户意图。** 矛盾或孤立记录不能证明用户选择了哪个来源。拒绝操作会保留证据，而不是创造新的替换决定。

## Consequences

自动升级可能停止并要求检查，而不是覆盖不兼容的手动选择。只有排除 optional 条目不会丢弃已有用户安装时，其失败才保持局部隔离。显式来源变更和损坏快照删除仍可通过指定名称的操作执行。

回归测试覆盖初始化保留、来源冲突、禁用声明、staged 与最终清单篡改、精确获取目标、产物损坏及文件系统大小写别名。发布代码的文件系统复现显式替换包管理器、获取与 Host 调用；它们不是打包应用验收，也不能把某次用户损失归因于重置或某个具体升级事件。

这些检查保护观察到的清单并保留可归因的操作证据，但不能重建未被记录的历史，也不能恢复首次捕获前已经被一致清空的清单。有歧义的旧恢复状态需要检查，而不是猜测提交或回滚。审计保留有上限，恢复副本不包含物化依赖，也不保证目录持久性。重新安装或恢复仍需要经过验证的输入和显式恢复决定。
