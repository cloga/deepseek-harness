# 发布脚本

[English](README.md) | 中文

本参考文档负责说明 [release.yml](../../.github/workflows/release.yml) 中受控的 Core/Web GitHub 产物发布路径。[families.ts](families.ts) 负责包成员、版本、载荷策略和发布顺序；现有 npm 发布器保持独立。

## 范围与前提

可选写入器仅接受 `cloga/deepseek-harness`、目标分支为 `review/issue-72-official-base` 的 PR（Pull Request）79，以及版本 `0.1.6-alpha.4`。它要求已获批准且已经存在的 `dsh-v<version>` 标签。它绝不会在持有写入令牌时执行 npm 发布、标签或引用写入、构建、安装或包生命周期脚本。后续版本需要经过审查的源码修改，而不是传入另一个未经校验的值。

原始 dsh 系列压缩包是 Core/Web 包产物，不是 Desktop 发行版、npm 发布或离线安装器。打包安装验证还使用此产物集合未包含的 vendored 框架和 Landlock 入口压缩包。这些配套包、可选原生平台包及其他注册表依赖仍属于外部安装依赖闭包。

只有在[规则集 API](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) 能够确认仓库自有的、针对这个确切标签的生效保护时，才允许发布：唯一包含条件必须为 `refs/tags/dsh-v<version>`，没有排除项、未知适用条件或更新例外，并明确禁止 `creation`、`update` 和 `deletion`。对于发布主体，`current_user_can_bypass` 必须明确为 `never`；缺失、未知或允许绕过的值都会拒绝发布。辅助脚本不要求读取仅管理员可见的全局绕过主体列表：其他主体的绕过权限并不授权发布器重建已删除的标签。如果工作流令牌无法读取所需的主体特定证据，发布就不可用；辅助脚本既不申请管理权限，也不接受保护检查覆盖参数。

GitHub 的创建发行版 API 可能隐式创建缺失标签，且没有原子的“仅允许已有标签”前提条件。辅助脚本会在创建前、草稿创建后、最终发布前和回读后，重新检查保护以及原始标签对象的类型和 SHA，而不只检查剥离后的提交。工作流互斥锁不会锁住人工写入者；这些读取无法排除管理员并发削弱保护，也无法检测删除后又恢复为完全相同引用对象的操作。操作者必须在授权发布前单独建立保护并禁止并发修改规则。未经回读，不声称存在任何保护或不可变发行版设置。

## 操作者输入

在确切的已批准标签上使用现有工作流的手动事件，并提供以下输入。默认分支上存在 `workflow_dispatch`，并不意味着指定引用接受这些新输入：必须先在禁用发布的情况下验证输入处理，再授权发布。此源码修改既不编辑默认分支，也不触发任何工作流。

| 输入 | 含义 |
| --- | --- |
| `publish_github_artifacts` | 布尔值，默认为 `false`；只有明确传入 `true` 才启用发布。 |
| `version` | 上述已批准的确切版本；标签和每个 dsh manifest（元数据清单）必须一致。 |
| `reviewed_head` | 已审查的最终 PR 头提交完整 SHA，并根据 GitHub PR 和审查事实核对。 |
| `merged_commit` | PR 合并提交的完整 SHA，必须等于剥离后的标签提交和 Actions 检出 SHA。 |
| `ci_run_id` | 针对该最终头提交、成功完成的 PR 专用 `ci.yml` 运行。 |
| `policy_run_id` | 针对该最终头提交、成功完成的 `issue-policy.yml` PR 运行。 |

输入用于选择 GitHub 记录，并不宣称已获批准或执行成功。GitHub 可能在合并后清空运行的 `pull_requests` 数组，因此只有在独立验证已合并 PR、确切最终头提交、成功工作流身份及实际被测试的检出树后，才接受空数组。非空数组必须包含所依据的 PR，且其头提交和目标分支完全匹配；缺失或格式错误的数组会被拒绝。写入器通过只读 GraphQL 查询读取传统分支保护和 PR 审查决定，通过 REST 读取生效规则集，并读取实际审查、检查和状态。它执行实际要求的批准数量；未要求批准时可以为零，不会凭空增加外部审查要求。必需检查保留传统保护及规则集中的应用绑定；头提交和被测试提交上的当前结果，包括同名旧式状态，不得与成功结论矛盾。必需检查和策略必须成功；可选的已跳过任务既不视为失败，也不视为测试证据。

## 源码与产物验证

对于 PR 工作流，Actions 的 `head_sha` 不是被测试的检出 SHA。写入器获取成功 CI 任务的日志，将解析范围限制在已知检出步骤及其时间范围内，并读取检出步骤的 `git log -1 --format=%H` 结果。每个被测试提交必须是 PR 头提交，或将该头提交列为父提交；其完整 Git 树和已审查头提交的树都必须等于标签的树。缺失、过期、歧义或未知格式的检出证据都会拒绝发布；没有操作者自报树的覆盖参数，也不会修改 CI 来制造证据。

发布运行中新执行的依赖布局和打包任务必须都成功。在现有官方构建、打包和打包安装命令之后，`github-artifacts-prepare.ts` 使用官方包系列定义，验证确切成员、规范顺序、根目录、成员及打包版本、文件名、安全归档路径、常规文件类型及载荷策略。随后，它在不重新打包的情况下生成 `release-manifest.json` 和 `SHA256SUMS`。扁平产物目录中不允许链接、重名、缺失成员或额外文件。

写入任务只下载同一次运行的打包任务输出的不可变产物 ID。普通 Node 执行 `github-artifacts.ts publish <directory> <journal>`，无需安装依赖。它再次验证该 ID 的源码与运行事实、封装记录、每个原始哈希和确切文件集合。唯一的写入权限是任务局部的 `contents: write`；Actions、检查、PR 和状态权限均为只读。PR 演练保留按引用取消的行为；发布工作流运行相互隔离且不会被取消，其写入任务另行串行执行。

## 失败与恢复

写入器在首次修改前立即检查标签身份，并确认不存在任何发行版或草稿。它创建预发行草稿，以每秒最多一次修改的速度串行上传原始文件以及顺序、哈希和源码运行元数据，然后验证远端的确切名称、大小、SHA-256 摘要和下载字节，再设置 `draft: false`、`prerelease: true`、`make_latest: false`。它要求公开仓库，在最终发布后再次回读产物和标签，然后通过不带认证的官方主机公开下载 URL 验证每个产物，包括校验和文件。只有公开可见性读取的 404 才会重试，总共最多三次；失败会报告发布验证未完成，而不重复修改操作。不可变发行版状态只根据实际发行版回读结果报告。

HTTP 失败、冲突、标签或产物变化，以及不确定的写入结果都会终止流程，不重试 POST、不替换、不删除，也不自动续传。带认证的请求绝不跟随重定向；允许列表内的下载重定向不携带认证。即使失败，任务也会将不含凭据的写入意图日志保留为 Actions 产物。上传失败会留下草稿；最终发布超时则可能已完成发布，未经回读不能声称仍保留为草稿。

不允许重新运行同一次工作流尝试。只要同一源码之前的写入器已经开始，新触发的工作流也会拒绝执行，即使尚看不到发行版。没有恢复开关：操作者必须核对确切的前次运行、日志、标签、发行版和产物字节，然后另外授权在自动写入器之外恢复。绝不要通过重新发送 POST 来判断先前请求是否成功。

## 验证范围

`github-artifacts.spec.ts` 使用 fake HTTP、私有临时文件、真实的小型 gzip 压缩包和普通 Node 防护入口，测试真实的准入与发布逻辑。工作流回归测试保留演练路由并约束写入器隔离。这些测试不证明真实 API 权限、触发输入行为、CI 日志保留情况、完整构建、打包安装、标签保护、发布或运行时验收。这些仍是前提条件或后续授权操作，不是单元测试通过即可给出的结论。
